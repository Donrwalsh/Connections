The last ~40 commits are almost entirely one activity: bringing a new LLM provider online (Google, Groq, OpenRouter, Mistral, SambaNova). Each one lands as a hand-copied stack of modules. SambaNova was 53 files, +2,600 lines. The codebase currently holds 75 near-identical per-provider files. Every candidate below is about turning that copied breadth into one deep module.

Before — five shallow stacks

After — one deep module + a config row

Problem
Every provider is a copied stack whose interface — isHeld, runTick, resume — is a fraction of its implementation; five copies already drift.

Solution
One ProviderPool module parameterised by a config record (strategy, queue names, hold semantics, pacing knobs); the frontend's providerPools.ts already proves the shape.

  • leverage: one interface, N providers
  • locality: hold/resume bugs concentrate in one module
  • interface is the test surface: one suite covers every pool
  • next provider = one config row, not 53 files
  • delete ~60 files; kill 4 ternary chains
  • drift between Groq and Mistral copies disappears

2 · One RateLimitHold table behind one hold interface

After — one table, one service, a discriminator

Problem
Groq/Mistral/Google/OpenRouter/SambaNovaRateLimitHold are byte-identical schemas; the services share the same six-method body and have already drifted in logging and comments.

Solution
One RateLimitHold entity keyed on (strategyName, modelName) — strategyName already names the provider — and one RateLimitHoldService.

  • interface shrinks; implementation absorbs the copies
  • locality: one query path to index and reason about
  • one hold spec, not five near-copies
  • smallest deletion-test-positive move; unblocks candidate 1

Before — cross-section of one run call

After — one seam

Problem
The runner re-derives the provider four times from strategyName and carries six hold-service dependencies to use one per run; solver.ts mirrors the same per-provider fan-out.

Solution
A providerPool(strategyName) lookup returning the pool's config and its hold port; the runner and the classifier read from it instead of branching.

  • locality: rate-limit shape for a provider lives in one record
  • leverage: add a provider without touching the runner
  • runner tests drop five hold-service mocks
  • rides on candidate 1 / 2; do it after, not before

4 · Fold the per-provider knob families in strategies.ts into the pool config

Worth exploring in-process
backend/src/strategies.ts (~730 lines)

Before — one knob family per provider

After — one record per pool

Problem
strategies.ts has grown a per-provider family of ~3-line env-reader functions; the file is now mostly boilerplate and every provider adds ~8 more.

Solution
One typed poolConfig(pool) record parsed once from env, indexed by pool id — the same list candidate 1 introduces.

  • interface shrinks: one config reader, not 40
  • leverage: the pool list is the single source of provider knobs
  • speculative until candidate 1 lands the pool list

Top recommendation

Start with candidate 2 — unify RateLimitHold — then take candidate 1.

Candidate 2 is the smallest move that passes the deletion test cleanly: five byte-identical schemas and five six-method services collapse into one table with a strategyName discriminator that already exists, behind one interface that becomes the whole test surface for holds. It is one migration and carries little risk. It also lays the seam that candidate 1 builds on — once the hold is one module, the dispatch tick and the RPD-resume sweep are the only per-provider copies left, and folding them into a config-driven Provider Pool module turns "53 files to add SambaNova" into "one config row." Candidates 3 and 4 are cleanup that rides on that pool list; do them last.

One constraint for candidate 1's design: OpenRouter's hold is account-wide with a heldReason() of "daily" | "per-minute-cooldown" and no model parameter, while the others are per-model. The pool config needs a scope: "account" | "model" field rather than assuming per-model everywhere.
