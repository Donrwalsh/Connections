Resolve provider behaviour through a pool lookup, not strategyName ternaries

Own analysis, pre-grilling. Rides on the config list from candidates 1–2; do it after them.

The friction

llm-strategy-runner.service.ts re-derives "which provider is this" from strategyName four separate times in one method, and carries six constructor-injected hold services to use at most one per run. Provider knowledge leaks across the runner instead of sitting behind one seam.

Each new provider adds a branch to all of these. They are physically far apart, so it is easy to update four and miss the fifth — and nothing fails loudly when you do (the run just calls the wrong fallback or the default OpenAI path).

Note Mistral is absent from the first ladder — its hold write is a fourth if 40 lines lower, gated on a different (heuristic-derived) code. That asymmetry is exactly the kind of bug this shape invites.

The deepened shape

One lookup at the top of runLlmStrategy. The pool carries everything the four ternaries and the ladder were deriving. 

const pool = providerPool(strategyName);   // null ⇒ deterministic/shuffle, unchanged path

// orchestrator call
await orchestrator.solveAssist(messages, model, pool.orchestratorProvider, contextWindow);

// top gate
if (pool.freeTier && await holds.isHeld(strategyName, pool.freeTier.holdScope === "model" ? model : undefined)) { … }

// fallback wait
const waitSeconds = pool.freeTier?.rateLimitFallbackSeconds() ?? DEFAULT_FALLBACK;

// write the daily hold — one call, pool decides the details
if (effectiveCode === "rate_limited_daily" && pool.freeTier) {
  await pool.freeTier.writeDailyHold(holds, { strategyName, model, error: outcome.error });
}

queueForStrategy becomes queues.get(providerPool(name)?.queues.runs ?? "strategy-runs"). The 7-member provider union in orchestrator.service.ts becomes an import of ModelProvider from one place. solver.ts's five 429 blocks stay as a Record<ModelProvider, Classify429> map keyed by provider — still five functions, but a table lookup instead of an if chain, and TypeScript's exhaustiveness check now flags a missing provider.

What sits behind the seam

The runner no longer knows provider names. It knows "there is a pool, it has a free tier, the free tier can gate a run and write a hold." Which hold service, which fallback constant, which reset-seconds computation, per-model vs account scope, Mistral's streak heuristic — all behind pool.freeTier. The solver.ts classifier map is behind classify429[provider].

Tests that survive, and improve

  • llm-strategy-runner.service.spec.ts injects one ProviderPool fake instead of six hold-service mocks — the interface is the test surface.
  • "Mistral parks after N consecutive 429s" and "OpenRouter writes an account hold at UTC-midnight fallback" become unit tests against the pool's writeDailyHold / classifyExtra, not integration tests threaded through the whole run loop.
  • A new provider needs no new runner test — it needs a config-row assertion.
  • The solver.ts classifier map gets a table-driven spec: one row per provider, same assertions.

Risks & open questions

Depends on candidates 1–2. Without the pool config list and the unified hold table, this just moves the ternaries into a factory. Sequence it last of the three.

The null path must stay exact. providerPool(name) returns null for alphabetical, shuffle-smart, etc. Every call site needs the same "fall through to the shared queue / default provider / no gate" behaviour the ternaries' trailing : "openai" and return defaultQueue give today. Cover deterministic strategies explicitly.

writeDailyHold as a function on a config object means the config module imports the hold service type — watch for a circular import between provider-pool and strategy. Keeping writeDailyHold as a pure descriptor ({ scope, fallbackSeconds, resetFrom }) that the runner interprets avoids the cycle; decide during grilling.

Ollama has a pool but no free tier. pool.freeTier is null for it and for OpenAI — the gate and hold-write blocks must no-op, matching today's "not in any ternary" behaviour.

Recommendation

Worth exploring, as the finishing move after 1 and 2. On its own it is a lateral change; on top of the pool config it is what makes "add a provider without touching the runner or the classifier" true, and it lets TypeScript catch a forgotten branch.
