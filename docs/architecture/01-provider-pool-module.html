Architecture deepening · candidate 1 of 4

Collapse the per-provider free-tier stack into one Provider Pool module

Own analysis, not yet grilled. Vocabulary: module · interface · depth · seam · adapter · leverage · locality from the codebase-design glossary; provider pool from the frontend's providerPools.ts.

The friction

Bringing a provider online means hand-copying a stack of ~15 files. The copies are not "similar" — they are the same file with a name substituted. Normalised diffs:

  • google-free-dispatch.service.ts vs groq-free-dispatch.service.ts — differ only in the strategy constant, the queue token, the state-row id string, and one comment.
  • groq-rate-limit-hold.service.ts vs mistral-rate-limit-hold.service.ts — differ only in the entity type and log wording.
  • 1782…-add-groq-rate-limit-hold.ts vs 1792…-add-mistral-rate-limit-hold.ts — identical DDL; differ only in the class name and comment.
  • GroqDispatchWidget.tsx vs MistralDispatchWidget.tsx — ~4 lines of real difference.

Each of these modules is shallow: its interface — isHeld() · runTick() · runResume() — is a thin slice of its copied implementation. Five copies have already drifted (Groq's resume logs "RPD hold set", Mistral's logs "hold set"; Google stamps resume job-ids with pacificDateStamp(), the others with triggerJobId). Deletion test

Delete GroqFreeDispatchService, GroqRpdResumeService, GroqRateLimitHoldService, their entities, their two queues, their module. Does the complexity concentrate or just move? It concentrates — the behaviour merges into the shape the Google copies already have; nothing new appears at a call site. That is the signal to deepen.

What actually varies between providers

The skeletons (tick chain, resume sweep, hold-table CRUD, worker registration, queue wiring, automation leg) are identical. The real variation is a small, closed set of enumerated axes — each already chosen by two or more providers, so each seam is real, not hypothetical:

The deepened shape

One config list — the backend twin of frontend/src/data/benchmark/providerPools.ts, which already established "adding a provider = adding one row" — plus three generic modules that read it. Not one module: three deep ones, each replacing a family of five. 

// backend/src/modules/provider-pool/provider-pool.config.ts
type HoldScope = "model" | "account";

type ResetSchedule =
  | { kind: "fixed-cron"; pattern: string; tz: string }   // google, openrouter
  | { kind: "self-rearm"; maxDelayMs: number };            // groq, mistral, sambanova

type DispatchSpec =
  | { stop: "until-held"; pacing: "shared" | { tickMs; maxBatch; maxInFlight } }
  | { stop: "account-budget"; budget; callsPerTrial; tickMs; maxBatch; maxInFlight; rpmCooldownMs };

interface ProviderPool {
  id: ProviderPoolId;                 // "google" | "groq" | ...  (shared with frontend list)
  strategyName: string;               // "llm-google"
  orchestratorProvider: ModelProvider;// "google"
  queues: { runs: string; freeDispatch: string; rpdResume: string };  // keep existing names
  freeTier: null | {                  // null for ollama / openai
    holdScope: HoldScope;
    resetSchedule: ResetSchedule;
    dispatch: DispatchSpec;
    rateLimitFallbackSeconds: () => number;
    dailyHoldFallbackSeconds?: () => number;
    classifyExtra?: (state, outcome) => HoldDecision | null;  // mistral's streak heuristic
  };
}

export const PROVIDER_POOLS: ProviderPool[] = [ /* one row per provider */ ];
export function providerPool(strategyName: string): ProviderPool | null;

What sits behind the seam

The seam is providerPool(strategyName) plus the three service interfaces. Callers name a pool and get behaviour. Hidden behind it: the single hold table and its scope rule, the tick chain and its stop-condition strategy, the resume sweep and its schedule registration, the BullMQ queue handles, the 429 classification. A new provider never touches the runner, the worker, the automation service, the controller, or the queue module — only the config list and (if it needs bespoke 429 parsing) solver.ts.

Migration path — each step ships on its own

  1. Unify the hold table (candidate 2). Smallest move; one migration; unblocks the rest.
  2. Add PROVIDER_POOLS + providerPool() to the backend. Pure addition, no behaviour change. Mirrors the frontend file.
  3. Replace the provider ternaries in llm-strategy-runner.service.ts and strategy.queue.ts's queueForStrategy with config lookups (candidate 3).
  4. Unify RpdResumeService behind runResume(poolId, jobId); drive scheduling from resetSchedule. Delete 5 services + 5 bootstraps → 1 + 1. Keep the 5 queue names.
  5. Unify FreeDispatchService behind runTick(poolId); add a pool column to the (also unified) dispatch-state table; select the stop condition from dispatch.stop. Delete 5 → 1.
  6. Loop the wiring. worker.ts and daily-automation.service.ts iterate PROVIDER_POOLS. queue.module.ts generates 3 queues per pool.
  7. Fold the knob families in strategies.ts into the pool config (candidate 4).

Tests that survive, and improve

  • Five near-identical *-free-dispatch.service.spec.ts collapse to one that exercises the tick chain thoroughly, plus a table-driven provider-pool.config.spec.ts asserting each row's shape. The tick logic gets tested once, deeply instead of five times shallowly.
  • Same for the five *-rpd-resume.service.spec.ts and five *-rate-limit-hold.service.spec.ts.
  • llm-strategy-runner.service.spec.ts drops five injected hold-service mocks for one ProviderPool fake — the interface becomes the test surface.
  • Per-provider behaviour becomes a data fixture (a config row) rather than a code path, so "does Mistral park after 4 consecutive 429s" is a unit test against classifyExtra, not an integration test through the whole runner.

Risks & open questions

Table unification needs a data migration. Merging 5 *RateLimitHold and 5 *DispatchState tables into 2 with a pool column. Holds are transient (expire within 24h) and dispatch state is ephemeral, so a cutover that copies live rows then drops the old tables is low-stakes; worst case a few parked runs wait one extra reset. Decide: copy-then-drop, or drop-and-let-the-next-sweep-recover.

Never rename a live BullMQ queue. The 15 queue names (llm-groq-runs, groq-free-dispatch, groq-rpd-resume, …) stay as data in the config; the code goes generic around them. Renaming would orphan in-flight jobs on deploy.

OpenRouter is the widest deviation. Account-scope hold, self-counted call budget, per-minute cooldown. holdScope: "account" and dispatch.stop: "account-budget" must be first-class in the config, not special-cased in the generic code. It is one provider on those axes today — but it is a real external constraint (OpenRouter's free tier genuinely is account-wide), so model it, don't fake it.

Keep FreeTierDispatchService (OpenAI flagship/mini) separate for v1. Its stop condition is a token-budget percentage across named tiers — a third dispatch.stop shape. Folding it in is possible later; forcing it now widens scope and risk.

Ternary-to-lookup is not free. A config lookup that returns null for a non-pool strategy needs the same "fall through to default" handling the ternaries have today. Cover deterministic/shuffle strategies explicitly in tests.

Recommendation

Strong. The abstraction is not speculative — every axis is already exercised by multiple providers, and the frontend has already proven the config-list shape. Do it in the order above; each step is independently shippable and independently revertible. Expected end state: adding a provider is one config row, one solver.ts block if its 429s are exotic, and one frontend row — down from 53 files.
