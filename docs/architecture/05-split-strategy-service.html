Split strategy.service.ts along its four seams

Own analysis, pre-grilling. Pure mechanical extraction — no schema, no behaviour change, no external contract.

The friction

backend/src/modules/strategy/strategy.service.ts is 1,696 lines in one class with 15 constructor dependencies (8 BullMQ queues, 6 repositories, GameService, StrategyRunStore, SupportedModelService). It carries four unrelated jobs.

The tell: the consumers do not overlap. A grep of every caller's method use:

CallerMethods it usesJob
strategy.controller.ts getLeaderboard, getRunHistory, getRunDetail, getRunDetailByRunId, getGuessDetail, getRunsForPuzzle, getRunsForPuzzleId, getRecentActivity run-history read model
*-free-dispatch.service.ts ×6 triggerStrategyRuns, countInFlightByModel, countTodayDispatchByModel, findUnrunPuzzleDatesForModel dispatch support
dispatch.controller.ts triggerStrategyRuns, findUnrunPuzzleDatesForModel + deleteRun, deleteErroredRuns, countErroredRuns dispatch + maintenance
worker.ts runDeterministicStrategy deterministic solver

No locality: a change to getLeaderboard (~340 lines) and a change to the shuffle solver (runDeterministicStrategy ~140 + pickRandomGroup + combinatorics) land in the same file. Every dispatch service imports the whole 1,696-line class — and with it a transitive dependency on 6 repos and GameService — to call two methods. Understanding "how is the leaderboard built" means scrolling past dispatch routing and a random-group generator.

Deletion test

There is nothing to delete here — the friction is a missing cut, not a shallow module. The relevant question is the inverse: does extracting each job leave a coherent deep module behind? Yes. The read model is ~1,100 lines with one caller and a clear surface (controller DTOs in, JSON out). Dispatch support is ~300 lines with one shape (name a strategy + model, get runs queued / counted). The deterministic solver is ~200 lines that never touch a queue. Each has one reason to change.

What sits behind each seam

  • Read model: the leaderboard's 8-way Promise.all, the price-history join, the cache, DTO shaping, prompt reconstruction. Callers see LeaderboardDto etc. — never a repo.
  • Dispatch: the strategyName → queue routing (candidate 3's target), trial-number fan-out, the "how many are in flight / ran today" counting queries the free-tier cycles pace against.
  • Deterministic solver: the alphabetical / reverse / order / shuffle-smart / shuffle-foolish algorithms and the combination walk. No queue, no HTTP, no LLM.

Tests that improve

  • The deterministic solver's spec stops needing 8 mocked queues and a SupportedModelService stub to test a sort.
  • The read model's spec is repos-in / DTOs-out — no BullMQ in the fixture, so no --forceExit open-handle fight for that suite.
  • The dispatch spec covers exactly the surface the free-tier cycles depend on, in isolation from leaderboard SQL.
  • the interface is the test surface: each module's public methods are now a short, single-purpose list.

Migration path

  1. Extract DeterministicSolver first — smallest, one caller (worker.ts), zero queue deps. Move combinatorics.ts usage with it.
  2. Extract StrategyDispatch — move the 7 dispatch methods + queueFor + the 8 queue injections. Update the 6 dispatch services and dispatch.controller.ts to inject the new type. This is the piece candidate 1's provider-pool work will build on, so doing it now keeps that change small.
  3. What remains is the read model — rename the file, drop the now-unused queue injections, done.
  4. Decide maintenance: delete* methods mutate runs, so they fit StrategyDispatch better than the read model; or a tiny fourth provider.
  5. Each step compiles and ships on its own — the class is only ever split, never rewritten.

Risks & open questions

Shared private helpers. A few small helpers (date resolution via gameService.resolveDateToPuzzleId, isLlmStrategy, DTO mappers) are used across the jobs. Most already live elsewhere (strategies.ts, GameService); the DTO mappers move with the read model. Check for any that need to become a shared util rather than being duplicated.

Circular-import risk via strategy.dto.ts. dto/strategy.dto.ts currently imports from strategy.service.ts (grep shows it). Splitting is a chance to reverse that — DTOs should not import a service. Straighten it during the extraction.

Naming. "Read model" is precise but not in the codebase's vocabulary yet. If this proceeds, add the term to a CONTEXT.md (which doesn't exist yet) so future reviews use it.

Do it before candidate 1. Carving the provider-pool dispatch module out of a focused 300-line StrategyDispatch is far cleaner than carving it out of the 1,696-line god class.

Recommendation

Strong, and the first thing to do across both rounds. It is the lowest-risk change on the board — no data, no contract, no behaviour — and it makes candidates 1 and 3 smaller. The consumers already partition perfectly; the file just hasn't caught up.
