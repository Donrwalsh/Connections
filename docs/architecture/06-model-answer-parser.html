Give the model-answer parser one home

Own analysis, pre-grilling. The candidate with a real bug history: the same parser fixed twice.

The friction

The solve prompts ask the model for a ### GROUPS section (Category: / Words: per group) and a ### ANSWER section (one comma-joined line per group). Turning that text back into word groups is one contract. It is implemented four times:

The parenthetical-strip fix (models append "LOOK, TOUCH, SIGHT, SMELL (all senses)" onto the Words: line) landed in copy B first — commit cdd6b22 — and the solve-assist.ts comment now reads, verbatim: "mirrors llm-strategy-runner.service.ts's WORDS_PARENTHETICAL_RE on the backend, which had this same fix … but this parser didn't." Two fixes for one bug, months apart, because the concept has no owner.

orchestrator.service.ts's solveAssist mapper (lines 127–138) forwards response, groups, model, contextWindow, latencyMs, usage, requestBody, responseId, responseHeaders, responseBody — but not proposals. The runner then re-derives proposals + categories from data.response at line 434. And SolveAssistResponseSchema in types.ts documents neither proposals nor the raw-detail fields the code actually returns — the wire contract and the payload have drifted apart.

Deletion test

Delete parseGroupsSection and assist.ts's parser. Does the parsing concentrate or move? It concentrates into the orchestrator's parser, which already does most of the work — the runner just reads the fields it currently recomputes. The one piece that genuinely can't move is described under "constraint" below.

The deepened shape

The orchestrator owns the ### GROUPS / ### ANSWER grammar. Its solve response carries the full structured parse. The backend runner reads fields; it never re-parses raw text. 

// orchestrator/src/answer-parser.ts  — the single grammar
export interface ParsedAnswer {
  groups: string[][];                        // ### ANSWER lines, fallback to ### GROUPS words
  proposals: { category: string; words: string[] }[];
  categoryByGroup: Record<number, string>;
  textIssues: ("parentheticalStripped" | "groupCountOff")[];  // text-only, no board needed
}
export function parseAnswer(responseText: string): ParsedAnswer;

// types.ts — SolveAssistResponseSchema gains the structure it already computes
SolveAssistResponseSchema = AssistResponseSchema.extend({
  proposals, categoryByGroup, textIssues,    // + the raw-detail fields it already returns
  latencyMs, contextWindow, usage,
});

orchestrator.service.ts's mapper forwards the new fields. llm-strategy-runner.service.ts line 434 becomes const { proposals, categoryByGroup, textIssues } = data;. parse-groups-section.ts is deleted; backfill-issue-tags.ts imports parseAnswer from a small shared module (it is a pure function — the script can import it from either package, or from a tiny packages/answer-parser).

Two adapters justify the seam

The parser has two real consumers already: the live orchestrator call, and backfill-issue-tags.ts re-parsing historical rawResponseText. That is a real seam, not a hypothetical one — which is why the parser should be one importable pure function, not a method fused into either service.

Constraint: not all issue tags are text-only

SolvePromptIssueTag has four values. Two are pure text and move to the orchestrator: parentheticalStripped, groupCountOff. Two need the puzzle board and stay backend-side: wordNotOnList (is this proposed word one of the 16?) and unclassified (a failure shape relative to the expected remaining-group count). So the split is: the orchestrator returns the structured parse + textIssues; the backend's evaluateProposals adds the board-aware tags. The tag values are already a plain text[] column (no DB enum) specifically so a new tag needs no migration — moving strings across the wire is cheap.

Tests that improve

  • One parser spec instead of three partial ones (solve-assist.test.ts, assist.test.ts, and the backend's parse-groups-section.spec.ts each cover a slice).
  • A parenthetical-strip regression is a one-line addition to one table-driven spec — and it can't regress on only one side.
  • The runner spec stops needing raw ### GROUPS fixture strings; it asserts on structured input.

Risks & open questions

Where does the shared pure function live? Options: (a) orchestrator owns it, backend imports across the repo (the two are separate npm packages — a relative import or a tiny workspace package); (b) a packages/answer-grammar both depend on. (a) is less machinery; (b) is cleaner if more shared parsing appears. Grill this.

Wire-schema change is a real contract change. SolveAssistResponseSchema currently under-describes the payload; widening it is safe (additive) but should be done deliberately, with the orchestrator's app.test.ts asserting the new shape.

Historical rawResponseText must still re-parse identically. backfill-issue-tags.ts is documented as idempotent and deterministic against the exact live parser. Keep it pointed at the same function so that guarantee holds — this is the main reason the parser must stay a pure, importable unit.

assist.ts's parser is genuinely different (no ### headings). Unifying it means the /diagnose prompts and parser move to the same grammar as /solve-assist — which is candidate 7. Do 6 and 7 together.

Recommendation

Strong. This is the one item across both rounds with a documented "we fixed it twice" history — the clearest possible signal of a concept with no home. Pair it with candidate 7. Sequence after candidate 5 (so the backend runner's re-parse call site is in a focused module) but it is independent of the provider-pool work.
