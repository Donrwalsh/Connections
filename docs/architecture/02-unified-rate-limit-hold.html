Architecture deepening · candidate 2 of 4

One RateLimitHold table behind one hold interface

The smallest deletion-test-positive move, and the seam candidate 1 builds on. Own analysis, pre-grilling.

The friction

Five entities — GoogleRateLimitHold, GroqRateLimitHold, OpenRouterRateLimitHold, MistralRateLimitHold, SambaNovaRateLimitHold. Four of them are byte-identical schemas: 

@Entity("GroqRateLimitHold")
@Unique("UQ_…_strategyName_modelName", ["strategyName", "modelName"])
class GroqRateLimitHold {
  id: number;  strategyName: string;  modelName: string;
  heldAt: Date;  resetAt: Date;
}

The fifth, OpenRouterRateLimitHold, differs by one column (reason: "daily" | "per-minute-cooldown") and drops modelName — its free tier is account-wide. Each entity has a matching *RateLimitHoldService with the same six methods (hold · isHeld · heldModels · nextResetAt · clearExpired) and a matching migration whose DDL is identical to its siblings'. The services have already drifted in log wording and doc comments — a sign the copies are maintained by hand, badly.

Shallow: the interface (six small methods) is a fraction of five copied implementations. No locality: a change to hold semantics — say, indexing resetAt for the sweep query — is five edits in five files plus five migrations. RateLimitHold is referenced by 34 non-spec files today.

Deletion test

Delete the four per-provider hold entities and their services. The logic doesn't move to a call site — it concentrates into one RateLimitHold entity and one service. The only thing that was ever provider-specific — how resetAt is computed — already lives in the caller (.hold() takes resetInSeconds; the runner and the orchestrator's 429 classifier decide the number). Passes cleanly.

The deepened shape

One entity. strategyName already discriminates the provider — it holds "llm-groq", "llm-mistral", etc. — so no new column is needed for the per-model providers. modelName becomes nullable to absorb OpenRouter's account-wide row; an optional reason column carries OpenRouter's daily/cooldown distinction and is null for everyone else. 

@Entity("RateLimitHold")
@Unique("UQ_RateLimitHold_strategy_model", ["strategyName", "modelName"])
class RateLimitHold {
  id: number;
  strategyName: string;            // the discriminator — already present
  modelName: string | null;       // null ⇒ account-wide hold (openrouter)
  reason: string | null;          // "daily" | "per-minute-cooldown" | null
  heldAt: Date;
  resetAt: Date;
}

@Injectable()
class RateLimitHoldService {
  hold(strategyName, opts: { modelName?: string; reason?: string; resetInSeconds: number }): Promise<void>;
  isHeld(strategyName, modelName?: string): Promise<boolean>;
  heldReason(strategyName): Promise<string | null>;      // account-scope callers
  heldModels(strategyName): Promise<string[]>;
  nextResetAt(strategyName): Promise<Date | null>;
  clearExpired(strategyName?): Promise<string[]>;         // all pools, or one
}

Postgres treats NULLs as distinct in a unique index, so the per-model unique constraint keeps working and the single account-wide OpenRouter row coexists. If a stricter guarantee is wanted, a partial unique index on strategyName WHERE modelName IS NULL pins it to one row.

What sits behind the seam

One TypeORM repository, one set of queries, one place to add an index. The holdScope decision (per-model vs account) is the only branch, and it is driven by whether the caller passes a modelName — which the pool config from candidate 1 would supply. Callers stop importing five different hold-service classes.

Two implementations, or one?

"One adapter = hypothetical seam, two = real." Here there are two genuine hold shapes — per-model and account-wide — and both are exercised in production. That justifies a single service with a scope parameter rather than two services or an interface with two implementations: the shared surface (a row with heldAt/resetAt and an expiry sweep) dwarfs the difference (one nullable column).

Migration path

  1. New migration: create RateLimitHold; copy rows from all five legacy tables (INSERT … SELECT, mapping the absent modelName for OpenRouter to NULL and its reason across); drop the five legacy tables.
  2. Replace the five entities + five services with the one entity + one service. Update strategy.module.ts (one forFeature entry, one provider) and the ~34 referencing files — mostly a find-and-replace of the injected type.
  3. Collapse the five *-rate-limit-hold.service.spec.ts into one.
  4. Because holds expire within 24h, the copy step is optional — a "create new, drop old" migration with no data copy costs at most one extra reset cycle for currently-parked runs. Choose based on how much you dislike that.

Wins

  • interface shrinks; one implementation absorbs five copies
  • locality: one query path to index, profile, and reason about
  • one hold spec instead of five near-copies that drift
  • the seam candidate 1's FreeDispatchService and RpdResumeService both depend on
  • a new provider's hold is zero new files

Risks & open questions

Nullable modelName weakens the type. Per-model call sites must not forget to pass it. Mitigate with a narrow method surface: isHeld(strategy, model) for per-model, heldReason(strategy) for account — the pool config picks which the caller uses, so it is decided once per provider, not per call.

The unique-constraint semantics change subtly. Today each table has its own UQ(strategyName, modelName); unified, the constraint spans providers. That is fine — strategyName differs — but the migration's constraint name and the NULL-handling deserve an explicit test.

Do this before, not after, candidate 1. If the pool module lands first it will just have to be re-plumbed onto the unified table. Order matters.

OpenRouter's hold() has a precedence rule ("a per-minute-cooldown request is a no-op while a daily hold is live"). That logic moves into the unified service, guarded by reason != null, and needs its own test — it is the one piece of behaviour, not just schema, that is provider-specific.

Recommendation

Strong, and first. One migration, a mechanical type swap across ~34 files, five spec files become one. Low risk because the data is transient. It is the wedge that makes candidate 1 tractable.
