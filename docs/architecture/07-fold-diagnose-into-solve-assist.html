Fold /diagnose into the solve-assist step

Own analysis, pre-grilling. Small; pairs with candidate 6.

The friction

orchestrator/src/assist.ts (86 lines, runAssistStep, backs POST /diagnose) is a stripped, older copy of orchestrator/src/solve-assist.ts (213 lines, solveAssist, backs POST /solve-assist). Same skeleton — generateText → catch → classifyModelCallError → parse groups → throw on empty — with the same two hard-won tuning decisions (maxRetries: 0 so the AI SDK doesn't silently re-bill a doomed call; the strategy runner is the only retry layer). /diagnose is the frontend's in-game "AI Assist" button; /solve-assist is the backend strategy runner's per-step call.

The two parseAnswerGroups functions have already diverged — a model that answers with ### ANSWER (what the current prompts ask for) parses on the /solve-assist path and returns nothing on /diagnose.

Deletion test

Delete assist.ts. Where does its behaviour go? Into solveAssist called with no model/provider override and telemetry suppressed. Nothing new appears at the /diagnose route — it becomes a thin adapter that maps AssistRequestSchema onto the call and trims the response to { response, groups, model }. Concentrates.

The deepened shape

// solve-assist.ts — one step function
interface SolveAssistOpts {
  model?: string;
  provider?: ModelProvider;
  contextWindow?: number;
  abortSignal?: AbortSignal;
  captureTelemetry?: boolean;   // /diagnose passes false — skip include:{requestBody,responseBody}, latency, usage
}
export async function solveAssistStep(messages: ChatMessage[], opts: SolveAssistOpts = {}): Promise<SolveAssistResult>;

// app.ts — /diagnose is now a thin route
app.post("/diagnose", bodyLimit(...), async (c) => {
  const parsed = AssistRequestSchema.safeParse(await c.req.json());
  ...
  const r = await solveAssistStep(parsed.data.messages, { captureTelemetry: false });
  return c.json({ response: r.response, groups: r.groups, model: r.model }, 200);
});

AssistRequestSchema / AssistResponseSchema stay as the /diagnose wire contract (the frontend depends on the trimmed shape). SolveAssistRequestSchema already .extend()s AssistRequestSchema — the relationship is already modelled; only the two step functions are redundant. One ASSIST_TEMPERATURE = 0.7 const.

Wins

  • locality: the generateText tuning (maxRetries: 0, abort forwarding, error classification) lives in one function
  • one parser path for both endpoints — directly enables candidate 6
  • the next provider-behaviour fix to the model call is made once, not once-and-maybe-twice
  • deletion: ~86 lines + assist.test.ts merged into solve-assist.test.ts

Risks & open questions

The /diagnose response must not grow. The frontend consumes exactly { response, groups, model }. The route trims; the step function's richer return stays internal. Assert this in app.test.ts.

Parser unification changes /diagnose parsing behaviour. Today it only recognises a bare ANSWER: line. After, it recognises ### ANSWER and strips parentheticals — a strict superset, so existing good responses still parse, but confirm no frontend prompt relies on the old strictness. This is the same decision as candidate 6; take them together.

Telemetry-off path. include: { requestBody: true, responseBody: true } has a cost and /diagnose never persists anything — captureTelemetry: false should genuinely skip it, not compute-then-discard.

Low urgency on its own. Two small files, one live bug (the divergent parser) that candidate 6 also fixes. Worth doing, not worth doing alone.

Recommendation

Worth exploring, bundled with candidate 6. Together they leave the orchestrator with one model-call step and one answer grammar behind two thin routes.
