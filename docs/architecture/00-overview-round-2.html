Round 2 · 2026-09-09 · "anything beyond the provider-pool work?"

The provider-pool candidates (docs 01–04) covered the recent hot spot. Looking wider: the friction that remains is not copy-paste breadth, it is depth — one module carrying four jobs, and one concept (parsing a model's answer) with no home, so its bugs get fixed twice. Four candidates, ranked.

module seam leakage / double work deep module

5 · Split strategy.service.ts along its four seams

Strong in-process no migration
backend/src/modules/strategy/strategy.service.ts — 1,696 lines, one class
consumers: strategy.controller.ts · dispatch.controller.ts · worker.ts · the 5 *-free-dispatch.service.ts

Before — one class, four unrelated jobs

After — four modules, each deep in one thing

Problem
One class owns the frontend read model, the dispatch-cycle support surface, the deterministic solve algorithms, and run maintenance. No locality: a leaderboard change and a shuffle-solver change touch the same 1,696-line file, and every consumer imports the whole thing.

Solution
Cut along the four seams that already exist in the method list. The read model (the bulk, ~1,100 LOC, consumed only by strategy.controller.ts) becomes its own module; dispatch support (consumed by the dispatch services + worker) another; the deterministic solver (consumed by the worker) a third.

  • locality: leaderboard logic lives with leaderboard logic
  • the interface is the test surface: the read model can be tested without a queue
  • the deterministic solver stops depending on TypeORM repos it never uses
  • leverage: candidate 1's dispatch work imports a 300-line module, not 1,700
  • pure mechanical extraction — no schema, no behaviour change
  • AI-navigability: four named files instead of one scroll

6 · Give the model-answer parser one home

Strong ports & adapters
orchestrator/src/solve-assist.ts — parseGroupProposals, parseAnswerGroups, WORDS_PARENTHETICAL_RE
orchestrator/src/assist.ts — a second, different parseAnswerGroups
backend/src/modules/strategy/parse-groups-section.ts — parseGroupsSection, its own WORDS_PARENTHETICAL_RE
backend/src/scripts/backfill-issue-tags.ts — re-parses stored rawResponseText a third time 
sequenceDiagram
  participant M as Model
  participant O as orchestrator/solve-assist.ts
  participant B as backend/llm-strategy-runner
  M->>O: raw "### GROUPS / ### ANSWER" text
  O->>O: parseGroupProposals + parseAnswerGroups
  O->>B: { groups, proposals, response: raw text }
  Note over B: ignores proposals,
re-parses response with parseGroupsSection
  B->>B: parseGroupsSection(data.response)  ⟵ same regex work again

Before — one contract, 3+ parsers, fixed twice

After — orchestrator owns it; backend consumes structure

Problem
Parsing a model's answer into groups is one contract implemented 3–4 times either side of the HTTP seam. The orchestrator returns proposals, the backend throws them away and re-runs the regexes on data.response. A parser bug (the parenthetical strip) had to be found and fixed twice.

Solution
The orchestrator owns the grammar. Its solve response carries the full structure the backend needs — groups, proposals, categoryMap, issueTags. The backend runner reads fields instead of re-parsing text. assist.ts collapses into the same call path (candidate 7).

  • locality: one grammar, one place a parser bug can hide
  • two adapters justify the seam: live orchestrator + the backfill re-parse
  • the regexes get one test suite, not three partial ones
  • the work stops being done twice per solve step
  • issue-tagging (PARENTHETICAL_STRIPPED, GROUP_COUNT_OFF) moves next to the parse that detects it
Constraint to grill: issueTags currently reference SolvePromptIssueTag, a backend enum. Either the orchestrator returns raw tag strings the backend maps, or the enum moves to a shared contract. The backend re-parse also exists partly so backfill-issue-tags.ts can retag historical rows — that path stays valid as long as the parser is an importable pure function, wherever it lives.

7 · Fold /diagnose into the solve-assist step

Worth exploring in-process
orchestrator/src/assist.ts (86) · orchestrator/src/solve-assist.ts (213) · orchestrator/src/app.ts (/diagnose, /solve-assist)

Before — two step functions, one drifted

After — one step, telemetry optional

Problem
assist.ts is a shallow stripped copy of solve-assist.ts — same generateText → classify → parse skeleton, minus provider selection, telemetry, and the abort signal. The two parseAnswerGroups have already diverged.

Solution
One step function with an optional-telemetry flag and provider ?? defaultProvider(). /diagnose keeps its route and request schema but delegates.

  • deletion test: delete assist.ts — behaviour concentrates, nothing new at the route
  • the abort-signal + maxRetries: 0 fixes stop needing to be made in two places
  • one parser path for both endpoints (pairs with candidate 6)
  • small — ~86 lines deleted, one test file merged

8 · Persist the prompt text instead of reconstructing it

Speculative schema change
backend/src/modules/strategy/prompt-reconstruction.ts (177) · llm-strategy-runner.service.ts (buildInitialPrompt / buildRetryPrompt) · entities/solve-prompt.entity.ts

Before — replay the run to show the run

After — store what was sent

Problem
The runner never stores the prompt it sends, so a 177-line module replays the run's state evolution to rebuild it for the UI. Its correctness is defined as "matches what the runner did" — a second implementation of the same logic, kept in sync by hand (the docstring enumerates the traps).

Solution
Add promptText to the SolvePrompt row the runner already writes per attempt. The chain view reads it. prompt-reconstruction.ts goes away.

  • locality: the transcript is data, not a derivation
  • deletes a module whose spec is "don't drift from the runner"
  • cost: full history per step is roughly quadratic in run length — measure a worst-case run's byte size first
  • cost: a backfill for historical runs still needs the reconstruction once, then it can be retired

Top recommendation

Candidate 5 — split strategy.service.ts — first, then candidate 6.

Candidate 5 is pure mechanical extraction: no schema, no behaviour change, no external contract. It has the widest payoff — the read model, the dispatch support (which candidate 1 leans on heavily), and the deterministic solver each get one reason to change and one set of callers, and a 1,696-line file stops being the thing every strategy consumer imports. Do it before the provider-pool work so candidate 1's dispatch module is carved out of something small.

Candidate 6 is the one with a real bug history — the same parser fixed twice — and it pairs naturally with candidate 7. Candidate 8 is worth a measurement (worst-case stored transcript size) before committing; if the number is fine, it deletes a fragile module outright.
