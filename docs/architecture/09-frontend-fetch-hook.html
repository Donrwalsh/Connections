A frontend data-fetching seam (useResource)

Own analysis, pre-grilling. The only round-3 item that stands on its own; independent of rounds 1–2.

The friction

frontend/src/ has 18 new AbortController() call sites across 13 files, and hooks/ holds exactly one hook — useConnectionsGame, a useReducer wrapper for game state, not data. Every component that reads the backend re-writes the same lifecycle by hand: 

// GuessChainVisualizer.tsx — one of 18 near-identical blocks
const [detail, setDetail] = useState<StrategyRunDetail | null>(null);
const [isLoading, setIsLoading] = useState(true);
const [error, setError] = useState<string | null>(null);
useEffect(() => {
  setIsLoading(true); setError(null); setDetail(null);
  const controller = new AbortController();
  fetchRunDetail(runId, controller.signal)
    .then((data) => { setDetail(data); setIsLoading(false); })
    .catch((err) => {
      if (err instanceof Error && err.name === "AbortError") return;   // remembered here…
      setError(...); setIsLoading(false);
    });
  return () => controller.abort();
}, [runId]);

The interface a component pays for this — three useStates, an effect with a dependency array, an abort cleanup, an AbortError swallow in the catch — is as large as the payload it wants ("call one endpoint"). That is the definition of a shallow pattern. And there is no locality: the race that happens when a dependency changes mid-flight, a forgotten controller.abort(), a stale-closure dep, a missing "reset state when the key changes" — each is a per-copy bug, invisible from any single place.

Deletion test

Replace the 18 blocks with useResource(key, fetcher). The abort / reset / race / loading / error handling concentrates into one hook; each component drops to a single line. The refreshSignal plumbing disappears into refetch(). Nothing moves to a call site — it moves out of every call site.

The deepened shape

// hooks/useResource.ts  (~40 lines)
interface Resource<T> { data: T | undefined; error: Error | undefined; loading: boolean; refetch: () => void; }

export function useResource<T>(
  key: unknown,                              // serialisable; a change aborts the old call + refetches
  fetcher: (signal: AbortSignal) => Promise<T>,
  opts?: { enabled?: boolean; keepPreviousData?: boolean },
): Resource<T>;

// behind the seam: one AbortController per key, a request-id counter so a
// stale resolve is ignored, state reset on key change unless keepPreviousData,
// AbortError swallowed, refetch() re-runs the fetcher with a fresh id.
// GuessChainVisualizer.tsx — after
const { data: detail, loading, error } = useResource(
  ["runDetail", runId],
  (signal) => fetchRunDetail(runId, signal),
);

// GuessSequencePanel.tsx — the Record<key,T> maps become one call per key,
// or a useResources([...keys]) sibling that returns a keyed map.

// PuzzleRunsPage.tsx — after a delete:
const { data: runs, refetch } = useResource(["runs", strategyName, puzzleId], ...);
// onDeleted={() => refetch()}  — no refreshSignal integer

Build vs adopt

The app is on React 19 / Vite 8 with no data-fetching library (checked package.json — no TanStack Query, no SWR). Two routes:

hand-rolled useResourceTanStack Query
new dependencynoneone (well-maintained)
coversabort, race, loading/error, refetch+ caching, dedup, focus-refetch, stale-while-revalidate, devtools
migrationwrite ~40 lines, swap 18 sites incrementallyadd QueryClientProvider, swap 18 sites, learn the model
fit~13 endpoints, mostly one-shot reads + a few polls — comfortably in scopepays off past ~dozens of interdependent queries with shared cache needs

Recommendation: hand-roll it for this app's size. Revisit TanStack only if the benchmark UI grows a real client-side cache requirement (e.g. the leaderboard and the run pages needing to share and invalidate the same data).

Tests that improve

  • One hard hook test — key change aborts the prior call, a stale resolve is ignored, refetch re-runs, unmount aborts — replaces the same assertions half-written across 13 component test files.
  • Component tests shrink to "given this data, render this" — no AbortController mocking, no fake-timer races.
  • The interface is the test surface: the hook's four-field return is the whole contract.

Risks & open questions

Key identity. A key that is a fresh array/object every render must be compared structurally (stable stringify) or memoised by the caller, or the hook refetches on every render. The hook should stringify internally and document it.

GuessSequencePanel's many-keys case is not a plain useResource — it fetches a list per strategy in parallel. Either call the hook N times (fine if N is a stable list) or add a useResources sibling. Grill which.

Game.tsx is different. Its AI-solve flow is an imperative action tied to game-reducer dispatches (aiSolveSuccess / aiSolveError), not a declarative read. Leave it; this candidate is about the read sites.

Incremental migration only. Convert one component per PR; the hook and the hand-rolled blocks coexist fine during the transition.

Recommendation

Strong. A genuine locality problem — 18 copies of one lifecycle, already subtly divergent — with a small, well-understood deepening. Independent of the provider-pool and strategy.service.ts work, so it can run in parallel with them.
