The provider-pool seam runs through the edge too

Own analysis, pre-grilling. This is candidate 1's finish line — do it as that work reaches the HTTP edge and the React tree, not standalone.

The friction

frontend/src/data/benchmark/providerPools.ts already establishes the config list — its own comment: "Adding a provider strategy to the backend means adding one row here — the pill, the filter chip, and the row description all derive from this list." That principle stops at the display layer. The dispatch-control path for the same providers is still hand-copied, five times, across four files on two sides:

FilePer-provider shape
backend/…/dispatch.controller.ts@Get("google") + @Delete("google") … ×5 (google, groq, openrouter, mistral, sambanova) — each body is return this.{p}FreeDispatchService.getStatus() / .stop(), plus 5 injected services
frontend/…/api.tsfetch{P}DispatchStatus() + stop{P}Dispatch() ×5 — each fetchJson("/dispatch/{p}") / fetchJson("/dispatch/{p}", {method:"DELETE"})
frontend/…/types.ts{P}DispatchStatus interface ×5 — four are "same shape as GroqDispatchStatus" per their own comments; OpenRouterDispatchStatus adds callsToday/dailyBudget
frontend/…/benchmark/{P}DispatchWidget.tsx×5 — normalised diff between any two is ~3 lines: a TITLE const, a doc comment, an aria-label

A sixth provider is four hand-edits past the config row — a route pair, a client pair, a type, a component — none of which candidate 1 (backend machinery) removes.

Deletion test

Delete GroqDispatchWidget.tsx, fetchGroqDispatchStatus, GroqDispatchStatus, the @Get/@Delete("groq") pair. Behaviour concentrates into one generic route, one client function, one component parameterised by a pool row. Only OpenRouter's extra fields need somewhere to go — covered below.

The deepened shape

// backend — one route pair, delegating to candidate 1's unified FreeDispatchService
@Get("pool/:poolId")    getPoolDispatchStatus(@Param("poolId") id: string) { return this.freeDispatch.getStatus(id); }
@Delete("pool/:poolId") stopPoolDispatch(@Param("poolId") id: string)      { return this.freeDispatch.stop(id); }
// keep /dispatch/google … as one-line shims for a release, then remove

// frontend/api.ts — one pair
export const fetchPoolDispatchStatus = (poolId: ProviderPoolId, s?: AbortSignal) =>
  fetchJson<PoolDispatchStatus>(`/dispatch/pool/${poolId}`, s);
export const stopPoolDispatch = (poolId: ProviderPoolId, s?: AbortSignal) =>
  fetchJson<PoolDispatchStatus>(`/dispatch/pool/${poolId}`, s, { method: "DELETE" });

// frontend/types.ts — one shape, optional account-budget fields
interface PoolDispatchStatus { active: boolean; startedAt: string | null;
  callsToday?: number; dailyBudget?: number; }   // present only for account-scope pools

// one component, rendered from the list — GuessSequencePanel already does this for toggles
{PROVIDER_POOLS.map((pool) => <PoolDispatchWidget key={pool.id} pool={pool} />)}

PoolDispatchWidget reads pool.label / pool.constraintBlurb from the row (add the blurb field) and shows the budget bar only when dailyBudget is present — the one real display difference, driven by data instead of by a separate file.

Minor, same family: queueForJudgeProvider

strategy.queue.ts has queueForStrategy(...8 queues..., name) and a second, narrower queueForJudgeProvider(provider, openAI, ollama, google) — both map a provider to its BullMQ queue, but the judge version only knows three providers. A side effect: a category-judge can't run on groq / openrouter / mistral / sambanova even though the solve path supports all seven. Candidate 3's providerPool(strategyName).queues.runs lookup replaces both and removes the asymmetry at no extra cost. Fold this into candidate 3.

Wins

  • leverage: a provider is one config row, backend to pixel
  • the DispatchStatus union collapses to one shape
  • the widget's poll logic is written once (pairs with candidate 9)
  • the judge path silently gains four providers

Risks

  • needs candidate 1's unified FreeDispatchService underneath — order after it
  • keep the old /dispatch/{provider} paths as shims for one release; the frontend is deployed together so the window is short
  • poolId in the URL must be validated against PROVIDER_POOLS (reject unknown) — a route param is user input
  • small on its own; real value is closing candidate 1 cleanly

Recommendation

Worth exploring, sequenced as the last step of candidate 1. On its own it is a modest dedup; as candidate 1's finish line it makes "one row per provider" true from the database to the DOM.
