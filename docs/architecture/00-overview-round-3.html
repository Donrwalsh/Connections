9 · A frontend data-fetching seam (useResource)

Strong frontend in-process
frontend/src/components/GuessSequencePanel.tsx · benchmark/GuessChainVisualizer.tsx · benchmark/*DispatchWidget.tsx ×5 ·
benchmark/FreeTierBudgetWidget.tsx · benchmark/CategoryJudgingWidget.tsx · pages/benchmark/PuzzleRunsPage.tsx · StrategyPuzzlePage.tsx · pages/PuzzlePage.tsx · components/Game.tsx
— 18 hand-rolled new AbortController() fetch blocks across 13 files; hooks/ holds exactly one hook (useConnectionsGame)

Before — every component re-writes the fetch lifecycle

After — one hook owns the lifecycle

Problem
The fetch lifecycle — abort on unmount, reset-on-dep-change, out-of-order-response guarding, loading/error state, post-mutation refetch — is re-implemented in every component. The interface (data/loading/error/refetch + a cleanup) is as big as the payload ("call one endpoint"). No locality: a race-condition fix has 18 sites.

Solution
One useResource(key, fetcher) hook (or a small library) that owns the lifecycle. Components declare a key and a fetcher and read { data, loading, error, refetch }. The refreshSignal counter convention — currently passed between FreeTierDispatchModal, FreeTierBudgetWidget, PuzzleRunsPage — collapses into refetch().

  • locality: abort / race / reset logic in one place
  • the interface is the test surface: test the hook once, hard
  • leverage: one fix (e.g. retry-on-focus) reaches every fetch
  • components shrink to markup + a one-line data call
  • the 5 *DispatchWidget polls become trivially identical (feeds candidate 10)
Grill: build vs adopt. A ~40-line useResource keeps the dependency count at zero and is easy to test; TanStack Query brings caching/dedup/focus-refetch for free but is a real dependency and a migration. The app has ~13 fetch sites — likely below the line where the library pays for itself, but worth a deliberate call.

10 · The provider-pool seam runs through the edge too

Worth exploring extends candidate 1
backend/src/modules/dispatch/dispatch.controller.ts — GET+DELETE /dispatch/{google,groq,openrouter,mistral,sambanova}
frontend/src/data/benchmark/api.ts — fetch{P}DispatchStatus + stop{P}Dispatch ×5
frontend/src/data/benchmark/types.ts — {P}DispatchStatus ×5
frontend/src/components/benchmark/{P}DispatchWidget.tsx ×5 (~4 lines of real difference each)

Before — the pool list stops at the backend services

After — the list drives the edge

Problem
Candidate 1 collapses the backend provider stacks, but the same per-provider shape is hand-copied at the HTTP edge and all the way into the React tree. providerPools.ts already exists as the list — the routes, the client, and the widgets just don't read it.

Solution
One /dispatch/pool/:poolId route pair (keep the old paths as shims), one fetchPoolDispatchStatus(poolId) / stopPoolDispatch(poolId), one <PoolDispatchWidget pool={…}> rendered from PROVIDER_POOLS.map() (GuessSequencePanel already derives its provider toggles this way — follow that).

  • leverage: a provider is one config row end to end
  • the dispatch-status widget's poll logic is written once (needs candidate 9)
  • the DispatchStatus union in types.ts becomes one generic shape
  • small on its own — real value is as candidate 1's finish line
Minor, same family: strategy.queue.ts's queueForJudgeProvider(provider, …) is a second, narrower copy of queueForStrategy — it maps a provider to a queue but only knows openai | ollama | google, so a category-judge can't run on the other four providers. Candidate 3's pool lookup unifies both and removes that asymmetry for free.

11 · One home for retry / backoff / date helpers

Speculative backend
puzzle-ingestion.service.ts (delay, computeBackoff, isRetryableStatus, formatDate, addDays) · llm-strategy-runner.service.ts (delay, modelErrorBackoff) · {google,groq,mistral,sambanova}-rpd-resume.service.ts (REARM_MAX_DELAY, delay math) · strategies.ts (startOfTodayUtc, nextDailyAutomationRunAt)

Problem
"Sleep N ms", "exponential backoff with a ceiling", "is this HTTP status retryable", and "start of today in UTC" are each re-implemented in three-to-five files. Each copy is tiny, so none is painful — but a backoff-policy change (jitter, a different cap) is a multi-file hunt, and the copies have already diverged in their ceilings and jitter.

Solution
A backend/src/common/ pair: retry.ts (delay, backoff({attempt, base, cap, jitter}), isRetryableHttpStatus) and the existing startOfTodayUtc promoted out of strategies.ts into a time.ts. Callers import instead of redefining.

  • one backoff policy, tuned once
  • low leverage — the copies are small and rarely change
  • best done opportunistically while touching each file for candidates 1 / 5

Checked this round, found healthy — skip in future passes

  • supported-model/ — a genuinely deep module. OpenRouterClient (28 lines) is a real adapter; openrouter-metadata.util.ts (22) is pure parsers; supported-model.service.ts has focused, single-purpose methods. Nothing to deepen.
  • game/game.service.ts — minor: puzzleDateToId and resolveDateToPuzzleId are near-duplicates, and GameService.evaluateGuessOnPuzzle is a static on an injectable class. Cosmetic, not structural.
  • auth/, app.setup.ts — small, single-purpose, no friction.
  • The *.bootstrap.ts family — the four *-rpd-resume.bootstrap.ts are covered by candidate 1; the remaining three (daily-automation, puzzle-queue, model-metadata-refresh) share a shape but differ enough (cron vs startup-only) that a base class would be thin. Not worth it.
  • The 60+ migration files — many are one-liners (add-{provider}-models), but migrations are append-only history by design; consolidating them is not a deepening.

Top recommendation

Candidate 9 — the frontend fetch hook — is the only round-3 item that stands on its own.

It is a real locality problem (18 copies of one lifecycle) with a clean deepening and it is independent of everything in rounds 1–2, so it can proceed in parallel. Candidate 10 is the natural closing move for candidate 1 — do it when that work reaches the edge, not before. Candidate 11 is cleanup to fold in opportunistically.

Diminishing returns note: round 1 (provider pools, 01–04) and the strategy.service.ts split (05) are where the leverage is. Rounds 2–3 are progressively smaller. After candidate 9, the codebase is in good shape structurally — further passes will mostly surface style, not architecture.
