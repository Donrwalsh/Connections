Architecture deepening · candidate 8 of 8 (round 2, item 4)

Persist the prompt text; retire prompt-reconstruction.ts

Own analysis, pre-grilling. Speculative — gated on one measurement.

The friction

llm-strategy-runner.service.ts builds each step's prompt at lines 356–357 (buildRetryPrompt(...) / buildInitialPrompt(...)) and sends it — but never stores it. The SolvePrompt row keeps rawResponseText, full requestBody / responseBody jsonb, headers, token counts, latency, temperature — everything except the prompt.

To show a run's chain in the UI, prompt-reconstruction.ts (177 lines) replays the run: it recomputes the initial word order, walks the stored guesses to rebuild availableWords / lockedInGroups / lastFailedGuess at each step, and re-invokes buildInitialPrompt / buildRetryPrompt with those. Its correctness is defined as "produces exactly what the runner produced" — a second implementation of the runner's state machine. Its docstring is ~40 lines of caveats: CALL_ERROR rows that must not advance state or they "would corrupt every later step's reconstruction", rows sharing a promptNumber, the full-transcript-per-step concatenation.

This is the exact anti-pattern the review brief names: a pure function extracted for testability, where the real bug risk is in how faithfully it mirrors the caller. There is no locality — a change to buildRetryPrompt or to the runner's state handling silently makes every historical run's displayed prompt wrong.

Deletion test

Delete prompt-reconstruction.ts. What replaces it? A column read. The runner already holds the exact string; writing it to the row it already INSERTs removes the need to ever re-derive it. Concentrates — from a 177-line replay module to a SELECT.

The data is arguably already persisted

SolvePrompt.requestBody (jsonb) is populated on every attempt from data.requestBody — the provider request body, captured via include: { requestBody: true }. That body contains the full messages array sent to the model. So the transcript is on the row already, just as a provider-shaped blob rather than the [User] / [Assistant] format the UI wants. Two framings follow:

  • Cheapest: render the chain view from requestBody.messages when present; keep reconstruction only as the fallback for rows that predate include: { requestBody: true }.
  • Cleanest: add a dedicated promptText text column the runner writes from the string it already built at line 356 — unambiguous, provider-independent, no jsonb spelunking. Reconstruction becomes a one-time backfill, then deletes.

The deepened shape (cleanest framing)

// solve-prompt.entity.ts
@Column({ type: "text", nullable: true })
promptText: string | null;   // the exact text sent this attempt; null only for pre-migration rows

// llm-strategy-runner.service.ts — it already has the value
const prompt = isRetry
  ? buildRetryPrompt(run.availableWords, state.lockedInGroups, state.lastFailedGuess, N)
  : buildInitialPrompt(run.availableWords, N);
// ...on every pendingPrompts.push({ ... }):
pendingPrompts.push({ ..., promptText: fullTranscriptSoFar + prompt });

// strategy read model (candidate 5) — chain view is now a projection
solvePrompts.map(p => ({ ...toDto(p), reconstructedPrompt: p.promptText }));

buildInitialPrompt / buildRetryPrompt stay exactly as they are — they are the builders. What goes away is the second caller that exists only to re-run them.

The gating measurement

The runner sends the entire conversation on every call, so storing the full transcript per step is roughly quadratic in run length: a run with k steps stores ~k²/2 prompt-lengths of text. Before committing, measure a worst-case real run: 

-- bytes of transcript we'd store for the longest runs
SELECT "strategyRunId",
       count(*) AS steps,
       sum(length(coalesce("rawResponseText",''))) AS response_bytes
FROM "SolvePrompt"
GROUP BY "strategyRunId"
ORDER BY response_bytes DESC LIMIT 20;

If the worst case is a few hundred KB, store it and move on. If it's multi-MB, store only the step's own newly-built prompt per row (linear) and let the read model concatenate for display — still no replay of runner state, just string joins.

Risks & open questions

Historical rows. Runs solved before the column exists have no promptText. Options: keep reconstructSolvePrompts alive purely as the null-fallback (defeats the deletion), or run it once as a backfill script writing promptText into old rows, then delete it. The backfill inherits reconstruction's fidelity caveats — but only once, against frozen data.

Store the step prompt or the full transcript? The quadratic concern. Linear (step-only) plus read-model concatenation is the safer default; full-transcript only if the measurement says it's cheap and the simpler read is worth it.

CALL_ERROR rows. Today reconstruction gives them a "what would have been sent" prompt without advancing state. With a stored column, the runner writes the prompt it actually built for that attempt — which is more accurate, and removes the special case entirely.

Depends on candidate 5. The read side of this lives in the run-history read model; do it after that split so the change lands in a focused file.

Recommendation

Speculative — run the query first. If worst-case transcript size is modest, this is a clear win: a fragile 177-line replay module whose spec is "never drift from the runner" becomes a column write and a read. If size is a problem, the linear variant still retires the module for a bit more read-model code. Either way, sequence it last — after candidate 5, and ideally after candidate 6/7 so the orchestrator side is settled.
