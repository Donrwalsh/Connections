Fold the per-provider knob families in strategies.ts into the pool config

Own analysis, pre-grilling. The smallest and most optional of the four — speculative until candidate 1 lands the config list.

The friction

backend/src/strategies.ts is ~730 lines. Beyond the genuine shared logic (trial counts, prompt limits, temperature, the daily-automation cron), it has grown a per-provider family of roughly 28 accessor functions, each a three-line wrapper of the same form: 

export function llmGroqRateLimitFallbackSeconds(env = process.env): number {
  return positiveTrialCount(env.LLM_GROQ_RATE_LIMIT_FALLBACK_SECONDS,
                            DEFAULT_LLM_GROQ_RATE_LIMIT_FALLBACK_SECONDS);
}

Each new provider adds ~6–10 more. The file is now mostly boilerplate, and the accessor name is the only thing tying an env var to the provider that reads it — there is no one place that says "here is everything tunable about Groq."

What is not the problem

The env-var surface is fine — operators legitimately tune LLM_GROQ_CONCURRENCY independently of LLM_MISTRAL_CONCURRENCY, and config/env.ts already documents them. The shallowness is the 28 hand-written functions that each do read env / coerce / default — an interface (28 named getters) nearly as large as its implementation (one positiveTrialCount call each).

The deepened shape

One typed record per pool, resolved once from env, hung off the same PROVIDER_POOLS list candidate 1 introduces. One generic reader; the env-var name is derived from the pool id. 

// provider-pool.config.ts
interface PoolKnobs {
  concurrency: number;                 // LLM_<ID>_CONCURRENCY
  rateLimitFallbackSeconds: number;    // LLM_<ID>_RATE_LIMIT_FALLBACK_SECONDS
  dailyHoldFallbackSeconds?: number;   // LLM_<ID>_DAILY_HOLD_FALLBACK_SECONDS
  dispatch?:
    | { pacing: "shared" }                            // reuse FREE_TIER_DISPATCH_*
    | { pacing: "dedicated"; tickMs; maxBatch; maxInFlight; rpmCooldownMs? };
  accountBudget?: { dailyBudget; callsPerTrial };  // openrouter only
  streakHeuristic?: { attempts; elapsedMs };       // mistral only
}

function poolKnobs(pool: ProviderPool, env = process.env): PoolKnobs {
  const ID = pool.id.toUpperCase();
  return {
    concurrency: intEnv(env, `LLM_${ID}_CONCURRENCY`, pool.defaults.concurrency),
    rateLimitFallbackSeconds: intEnv(env, `LLM_${ID}_RATE_LIMIT_FALLBACK_SECONDS`, 60),
    …
  };
}

strategies.ts keeps its genuinely shared exports and loses the 28 wrappers plus their 28 DEFAULT_* consts (defaults move to the pool row). Callers change from llmGroqConcurrency() to poolKnobs(pool).concurrency — and by that point the caller already holds a pool (candidates 1–3).

Tests

  • ~28 tiny "reads env / falls back to default" specs become one parametrised poolKnobs spec: for each pool, assert the env override wins and the default applies.
  • The coercion edge cases (negative, zero, non-numeric) are tested once on intEnv instead of re-tested per accessor.

Risks & open questions

Derived env-var names hurt greppability. Today grep LLM_GROQ_CONCURRENCY finds the reader. With `LLM_${ID}_CONCURRENCY` it finds nothing. Mitigate: keep a static manifest (a plain array of the literal names per pool) that config/env.ts documentation and a startup validation both iterate — so the names still exist as literals in one place.

Some knobs genuinely resist templating. mistralPersistentRateLimitElapsedMs reads a seconds env and returns milliseconds; openRouterDispatchRpmCooldownSeconds reads ms and returns seconds. These unit conversions stay as small explicit functions on the record, not templated.

Lowest priority. This is pure boilerplate reduction with no behaviour or testability change to the running system beyond the spec collapse. It only pays off once 1–3 have introduced the pool object that callers hold. Do it last, or skip it if the pool config from candidate 1 already absorbs most of these inline.

Recommendation

Worth exploring / speculative. Real cleanup — ~28 functions and ~28 constants gone, one parametrised spec — but no leverage or locality gain that candidates 1–3 don't already deliver. Fold it into candidate 1's config work rather than running it as a separate pass.
