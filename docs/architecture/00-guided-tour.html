1What the product is

Connections Lab is two products in one app, and they share a database:

Half 1 — the game

A playable copy of NYT Connections. There are 16 words; the player picks 4, submits, and gets a colour-coded reveal. Four mistakes end the game. There's date navigation back to 2023-06-12, a share-grid, and an AI Assist button that asks an LLM to propose one group. Route: / and /puzzle/:date.

Half 2 — the benchmark

A leaderboard of strategies solving every historical puzzle. Brute-force strategies (alphabetical, shuffle, and so on) run automatically. LLM strategies run across eight provider pools (OpenAI, Google, Groq, OpenRouter, Mistral, SambaNova, NVIDIA NIM, Ollama), and every prompt, proposal and guess is recorded. Routes: /leaderboard/**, /activity, /maintenance.

Most of the code, and nearly all of the complexity, is in half 2. The expensive part is running LLM trials across a range of providers, many of them on free tiers with strict and poorly documented rate limits, and recording enough about each run to debug it afterwards. If some code looks over-engineered, it's usually because of a real provider behaviour that has already bitten the project once.

2The system map

Local dev — docker-compose.yml (compose project connections-dev)

The key split
The backend answers HTTP and enqueues. The worker does the work. It's a separate Node process started with npx tsx --watch src/worker.ts, and it boots the same AppModule as an application context with no HTTP listener. A slow LLM run never blocks a request, and the worker can be split across machines (stop 6).

Only the orchestrator talks to models
The worker never calls a model API. It posts the conversation to the orchestrator's /solve-step, and the orchestrator picks the provider, calls it with the AI SDK, classifies failures, and parses the text. All provider API keys live there and nowhere else. The one exception to "backend never talks to providers" is the OpenRouter metadata client in supported-model/, which only reads the public catalog.

Production (docker-compose.prod.yml, deployed via Coolify) has no Ollama. It runs the worker with WORKER_ROLE=cloud, and an optional WORKER_ROLE=ollama worker on someone's own machine pulls Ollama jobs from the deployed Redis (docker-compose.local-ollama-worker.yml). Production also runs Adminer on :8091. The containers you can reach locally are dev. You don't have direct access to production.

Controllers are thin
Controllers validate params (DTOs in dto/ with class-validator), call one service method, and map errors to HTTP. Business rules live in services, which is what the specs test. Read endpoints are grouped under /strategy/** and write endpoints under /dispatch/**.

Env access goes through functions
Tunables are read with small accessor functions (llmMaxPrompts(), shuffleTrialCount(), pool knobs as thunks) that take an optional env argument. They're read at call time, not snapshotted, so tests can override them per case. Add new knobs the same way.

Always write an explicit @Inject(Token) (or @InjectRepository / @InjectDataSource) on every constructor parameter. The worker runs under tsx/esbuild, which doesn't emit decorator metadata. A bare typed parameter silently resolves to undefined in the worker, yet it works under ts-jest and in unit tests. This has shipped as a bug more than once.

6The worker process

backend/src/worker.ts is short and worth reading in full. It creates NestFactory.createApplicationContext(AppModule), pulls services out with appContext.get(...), and registers one BullMQ Worker per queue. It isn't a Nest module and has no DI of its own. It's the glue between queues and services.

Queue(s)HandlerConcurrencyWhy
strategy-runsDeterministicSolver1Cheap and CPU-bound. Serialized so runs don't contend on DB writes.
llm-<pool>-runs ×8handleLlmJob → LlmStrategyRunner or CategoryEvaluatorLLM_<POOL>_CONCURRENCY (default 1)One queue per provider, so a slow or rate-limited provider never blocks another provider or the brute-force strategies. Judge jobs share the queue so they share the provider's rate budget.
puzzle-populationPuzzleIngestionService1Mutates the "latest date" cursor.
<pool>-free-dispatch ×5, free-tier-dispatchFreeDispatchService / FreeTierDispatchService .runTick1Each tick queues a batch, then schedules its own successor tick with a delay.
<pool>-rpd-resume ×5RpdResumeService1Clears expired holds and restarts parked runs once a daily quota resets.
model-metadata-refresh, daily-automationModelMetadataRefreshService, DailyAutomationService1Cron jobs.

WORKER_ROLE (all | cloud | ollama) chooses which of these a process registers. Crons are scheduled by *.bootstrap.ts providers using BullMQ job schedulers, so schedules live in Redis rather than in a Node timer.

Never rename a queue. Queue names are persisted in Redis alongside in-flight jobs, and renaming one orphans them. PROVIDER_POOLS keeps the historical names verbatim for this reason. Job ids are deterministic (runStrategyJobId = run-{puzzle}-{strategy}-{model}-{trial}, with colons stripped because BullMQ rejects them), so a double-enqueue collapses into one job.

7Life of a strategy run

The best way to learn the codebase is to trace one LLM trial end to end. Follow along in the files named below.

One LLM trial — POST /dispatch/model/gpt-4.1-nano/2025-01-01

The conversation is the state
Each step sends the full message history. The initial prompt (buildInitialPrompt) lists the remaining words and asks for a ### GROUPS block (Category/Words) followed by an ### ANSWER block. After each guess the runner appends feedback (buildRetryPrompt). A run can be resumed after a crash, a hold or a manual retry, because reconstructMessages rebuilds the history from the last persisted SolvePrompt.requestBody.

Failure is a first-class outcome
Each bad outcome has its own counter and cap: duplicates (LLM_MAX_DUPLICATE_GUESSES), malformed output (LLM_MAX_MALFORMED_RESPONSES), transient model errors with exponential backoff (LLM_MAX_MODEL_ERRORS), and wrong guesses (the NYT four-mistake rule). A per-minute 429 is never a failure: the run waits and retries forever. A daily-quota 429 parks the run as rateLimitedDaily and writes a hold.

StrategyRun.statusMeaningCan resume?
runningIn progress (or crashed mid-run; the maintenance page finds these).—
completedAll 4 groups found.terminal
failedHit the mistake limit.terminal
duplicateKept re-proposing guessed groups.terminal
malformedResponseOutput couldn't be parsed, several times in a row.terminal
errorToo many consecutive transport/model errors.yes, via manual retry (POST /dispatch/run/:id/retry)
rateLimitedDailyParked behind a daily-quota hold.yes, automatically, by the pool's RPD-resume sweep

The deterministic path is much simpler. DeterministicSolver.runDeterministicStrategy orders the 16 words (computeInitialWordOrder in strategy-run-store.service.ts), walks 4-combinations (combinatorics.ts) or random groups for the shuffles, and records a Guess for each attempt. It runs on the shared strategy-runs queue. Ingestion (PuzzleIngestionService) queues these automatically for every new puzzle, using AUTOMATIC_STRATEGIES and strategyTrialNumbers().

On the read side, RunHistoryReadModel (strategy-read.service.ts) builds the leaderboard (with a short in-memory cache), per-puzzle runs, run detail and recent activity. It's the biggest service. If a leaderboard number looks wrong, the bug is almost always here, in a SQL aggregate.

8Orchestrator & answer-grammar

RouteCallerDoes

provider.ts

ModelProvider union and getModel(provider, model, contextWindow), one branch per AI SDK provider package. Ollama's num_ctx is capped by MODEL_CONTEXT_WINDOW to avoid OOM.

solver.ts

SolveError and classifyModelCallError. The per-provider RATE_LIMIT_429_CLASSIFIERS tell a per-minute limit apart from a daily one, using each provider's real headers and body shape. The codes map to HTTP 409/400/429/502, and the backend maps them back.

answer-step.ts

One generateText call with maxRetries: 0 (the runner is the only retry layer) and the incoming request's abortSignal forwarded, so a backend timeout actually cancels the billed call.

packages/answer-grammar is the single parser for the ### GROUPS/### ANSWER text format. It returns groups (from ANSWER), proposalWords + categoryByGroup (from GROUPS), and textIssues (parentheticalStripped, groupCountOff and so on). The orchestrator uses it on the live response. The backend imports it too: LlmStrategyRunner uses formatCompactAnswer, and scripts like backfill-issue-tags.ts use it to re-parse historical responses. It was made a package because the two copies had drifted (docs/architecture/06-model-answer-parser.html). Every odd rule in it corresponds to a real model habit, and each one has a test.

Stale knobs. The temperature actually used for a solve is ANSWER_STEP_TEMPERATURE = 0.7, hard-coded in answer-step.ts. /solve-step's request schema has no temperature field. LLM_TEMPERATURE_BASE is only recorded on each SolvePrompt. LLM_NUM_RESPONSES and LLM_MAX_PROMPTS aren't read by anything outside strategies.ts. All three are still documented in .env.sample and the README. Don't tune them expecting a change in behaviour.

9Provider pools, rate limits & free tiers

This area went through the biggest refactor (docs/architecture/01–04). Adding a free-tier provider used to mean hand-copying ~15 near-identical files. Now the provider-specific differences are data: one row in PROVIDER_POOLS. Generic services read that row and branch on its fields, never on a provider's name.

PROVIDER_POOLS row — backend/src/modules/provider-pool/provider-pool.config.ts

{
  id: "groq", label: "Groq", strategyName: "llm-groq", orchestratorProvider: "groq",
  queues: { runs: "llm-groq-runs", freeDispatch: "…", rpdResume: "…" },   // verbatim, never renamed
  concurrency: () => intEnv("LLM_GROQ_CONCURRENCY", 1),               // thunks, read at call time
  freeTier: {                                                        // null for openai, ollama, nvidia
    holdScope: "model",                    // or "account" (openrouter)
    resetSchedule: { kind: "fixed-cron" | "self-rearm", … },
    dispatch: { stop: "until-held" | "account-budget", pacing },
    rateLimitFallbackSeconds, dailyHoldFallbackSeconds, persistentRateLimitPark?,
  },
}
  • Readers: the queue router (queueForStrategy), the worker's registration loops, LlmStrategyRunner's hold logic, FreeDispatchService, RpdResumeService, daily automation, and /dispatch/pool/:poolId.
  • Frontend twin: frontend/src/data/benchmark/providerPools.ts holds id/label/strategyName only. Parity tests stop the two lists drifting.
  • Holds: a daily 429 writes a RateLimitHold for a model (or the whole account, for OpenRouter). The runner checks the hold before each call and parks the run. The pool's resume sweep clears expired holds and re-queues parked runs.
  • Free-dispatch cycle: a tick counts in-flight runs, picks unrun puzzle dates for each unheld model, queues a small batch, then re-enqueues itself with a delay. It stops when every model is held (until-held) or when the day's call budget is spent (account-budget). State is kept in DispatchState.
  • OpenAI is different: OpenAI's free tier is a daily token allowance ("mini"/"flagship"), so FreeTierDispatchService budgets against FreeTierUsageService's token sums with a safety ceiling.
  • Rule for rate-limit code: classify from a real captured error, never from vendor docs. Until one has been captured, ship null (generic retry), as NVIDIA currently does. Check model availability against the account itself, too: NVIDIA's catalog listed models that returned 410.

12Database & migrations

Migrations only
synchronize: false, migrationsRun: true. An empty database is built from 1754400000000-initial-schema.ts onward when the backend or worker boots, so there's no SQL init script. Generate with npm run migration:generate (uses src/data-source.ts). Filenames are <timestamp>-kebab-name.ts. Migrations are append-only history: don't consolidate old ones or edit them.

Reference data lives in migrations too
New SupportedModel rows are added by migration (for example 1803000000000-add-nvidia-models.ts), with a doc comment saying why each model is included and how its openRouterSlug was confirmed. Pricing and context window are backfilled later by the metadata refresh. A worker that shares a DB with another instance sets DB_MIGRATIONS_RUN=false.

Hand-maintained registration lists. TypeOrmModule.forFeature([X]) alone isn't enough. A new entity must also be added to the entities: [...] arrays in both app.module.ts and data-source.ts. If you miss one, the first real query fails with EntityMetadataNotFoundError, even though unit tests and often e2e pass. Likewise a new queue must be added to Bull Board's list in app.setup.ts and to queue.module.ts. Every provider addition so far has needed a follow-up fix for one of these.

backend/src/scripts/ holds one-off backfills and repairs (backfill:*, trim:*, purge:*). They run from compiled dist/ with node, not tsx, so they work inside the production image. Each has a spec. Follow that pattern: a pure planning function that's tested, plus a thin script that applies the plan.

14Recipes

Make a new model dispatchable on an existing provider

  1. Confirm with a live call that the model works on our API account. Vendor catalogs are not reliable here.
  2. Add a migration that inserts SupportedModel rows (strategyName, modelName = provider's id, openRouterSlug if confirmed, freeTier if applicable). Copy the latest add-*-models migration.
  3. That's all. Dispatch is gated on SupportedModelService.assertSupported, and the UI reads /strategy/models.

Add a new provider pool

Use docs/specs/2026-09-21-nvidia-nim-provider-design.md as the template. It lists every file that had to change:

  1. orchestrator/package.json: the AI SDK provider package.
  2. orchestrator/src/provider.ts: ModelProvider union, getModel/getModelName/defaultProvider, default model.
  3. orchestrator/src/solver.ts: RATE_LIMIT_429_CLASSIFIERS.<id> (null until you have a real captured 429).
  4. backend/src/strategies.ts: LLM_<ID>, SUPPORTED_STRATEGIES, LLM_STRATEGIES.
  5. provider-pool.config.ts: the ProviderPoolId union and a new PROVIDER_POOLS row (freeTier: null to start).
  6. Queue wiring: strategy.queue.ts (new Queue), queue.module.ts (token + RUNS_QUEUE_BY_POOL), the injections in strategy-dispatch.service.ts / strategy-read.service.ts, and Bull Board in app.setup.ts.
  7. frontend/src/data/benchmark/providerPools.ts: the UI row (the parity test will fail until you add it).
  8. backend/src/config/env.ts: JUDGE_PROVIDERS. Env vars also go in .env.sample, the README table and all compose files.
  9. A migration that seeds its SupportedModel rows.

The worker picks up the new runs queue automatically from PROVIDER_POOLS. Free-tier automation (holds, resume, dispatch cycle) is a separate step, taken only once the provider's real rate-limit behaviour has been observed.

Add a backend endpoint

  1. Reads go on StrategyController → RunHistoryReadModel. Writes go on DispatchController → StrategyDispatch (or the relevant service), with DispatchAuthGuard if the route spends money or deletes data.
  2. DTO with class-validator in dto/, plus Swagger decorators (the docs at /api/docs are part of the contract).
  3. Explicit @Inject(...) on every new constructor parameter.
  4. A service spec next to the file. Extend e2e if routing or guards changed.
  5. Frontend: a typed function in data/benchmark/api.ts, types in types.ts, consumed through React Query.

Add an entity or column

  1. Entity in the feature module's entities/, plus TypeOrmModule.forFeature in that module.
  2. Add it to both entities arrays (app.module.ts, data-source.ts).
  3. npm run migration:generate, then review the SQL by hand. Don't touch the index and constraint names that the generator doesn't own.
  4. Restart the dev backend to apply it, and check a real query against the dev DB.

Change the solve prompt or the answer format

The prompts are in llm-strategy-runner.service.ts (buildInitialPrompt / buildRetryPrompt) for automated runs and in frontend/src/lib/aiAssistPrompts.ts for AI Assist. Both must keep producing text that answer-grammar can parse. Prompt text is persisted on each SolvePrompt, so historical runs keep the exact prompt they were given. A format change needs a grammar test first, then a grammar rebuild.

15Architectural decisions, and why

DecisionWhy
A separate worker process, not in-app BullMQ processorsLLM runs take minutes. Keeping them off the HTTP process makes the API responsive and lets the worker be split by role (cloud/ollama) across machines without exposing Ollama to the internet.
A separate orchestrator service for all model callsProvider keys are isolated in one small service, and the AI SDK dependency surface stays out of the backend. A second orchestrator can run next to a local Ollama, and it's the one place where provider error shapes get normalized.
One queue per providerProvider-level isolation: a rate-limited Mistral doesn't delay Groq or the brute-force strategies, and each provider gets its own concurrency. Judge jobs ride the judge provider's queue so they share its rate budget.
Provider differences as config (PROVIDER_POOLS)Adding a provider used to mean copying ~15 files. The row captures the small, closed set of axes that actually differ (hold scope, reset schedule, dispatch stop rule, pacing). docs/architecture/01.
Persist everything about every LLM callDebugging model behaviour after the fact needs the raw request/response, tokens and latency. Runs can be resumed from persisted history, and costs can be backfilled. This costs storage, and it's worth it.
Deterministic BullMQ job idsRe-dispatching the same trial is idempotent (issue #43 fixed a collision where the model wasn't part of the id).
LLM strategies never auto-dispatched from ingestionToken spend is always either a deliberate human action or a budgeted free-tier cycle with hard stop rules.
Per-minute 429 = wait forever; daily 429 = park + holdFree tiers make per-minute limits routine, and treating them as failures would poison the leaderboard. Daily limits would waste calls if retried, so the run parks until the reset.
Schema by migrations only; reference data by migrationsThe same mechanism boots CI, fresh dev databases and production, and the model allowlist is versioned with the code that relies on it.
Orchestrator app.ts / index.ts splitRoute tests call app.request() without binding a port.
Split of the old StrategyServiceA 1,700-line class had four jobs with non-overlapping callers. It's now DeterministicSolver / StrategyDispatch / RunHistoryReadModel. docs/architecture/05.

The docs/architecture/00-overview*.html reviews list known friction that hasn't been addressed yet, and modules already judged healthy. Read them before starting a refactor, so you don't repeat an analysis that's already been done.

16Gotchas

  • Bare constructor types resolve to undefined in the worker. Always use @Inject(Token).
  • Entity/queue registration lists: app.module.ts + data-source.ts + Bull Board in app.setup.ts.
  • npx jest hangs forever. Use npm test -- … with a bounded timeout.
  • answer-grammar changes are invisible until rebuilt (consumers import dist/). In Docker dev, packages/answer-grammar/src is bind-mounted but dist/ is built into the image. After a grammar edit, rebuild inside the backend/orchestrator containers (or rebuild the images) before trusting what the live stack does.
  • npm test in frontend/ is watch mode. Use npm run test:run.
  • The frontend's "proxy" field is for Docker networking. Local dev uses VITE_API_URL, which is baked in at build time.
  • WSL: inline env vars (DB_PORT=… npm …) don't reach Windows node.exe unless they're listed in WSLENV. Rely on test/setup-env.ts defaults instead.
  • Never rename a BullMQ queue or change a job-id shape casually. In-flight jobs are keyed by both.
  • Case matters in words. Models change capitalization, and puzzle words can have odd casing. Compare through normalize-puzzle-word.ts / case-insensitive-match.ts, not ===.
  • Model name ≠ unique. The same modelName can exist under two strategies (e.g. gpt-oss-20b on Groq and NIM), so always carry strategyName with it. The UI has an AmbiguousModelPicker for this.
  • "Today" is UTC for quotas (startOfTodayUtc) but local for the player's "today's puzzle". Don't mix them up.
  • Local containers are dev. Production is a separate Coolify deployment that you can't reach directly.

LocationContains

docs/superpowers/specs · plansFeature designs and plans from the Superpowers brainstorm → plan → execute workflow, dated. Good background reading for any feature area. Keep other design notes out of here, so the provenance of each doc stays clear.
  • Never commit to master directly, docs included. Branch as feat/…, fix/…, refactor/…, test/… or docs/… and open a PR. CI runs three workflows (backend, frontend, orchestrator).
  • Commit messages use Conventional Commits with a scope: fix(backend): …, test(frontend): …, docs(architecture): ….
  • Code comments explain why, and often cite the incident or design doc behind a decision. Match that density. When a comment and the code disagree, trust the code and fix the comment.

Suggested first week

Read the loop, run the loop, change the loop.

  1. Bring the stack up. Play a puzzle. Open Swagger and Bull Board and watch ingestion drain.
  2. Read worker.ts, provider-pool.config.ts and strategies.ts in full.
  3. Dispatch one Ollama trial (POST /dispatch/model/llama3.2/<date>, free and local), then follow it through LlmStrategyRunner, the orchestrator logs, and the SolvePrompt/LlmProposal/Guess rows it wrote. Then find it in the UI's guess-chain visualizer.
  4. Run all four test suites locally, including backend e2e.
  5. Skim docs/architecture/00-overview*.html and one Superpowers spec for the area you'll work on first.
  6. Pick a small change, such as a new column on a leaderboard table or a new grammar edge case, and ship it through a branch and PR.
